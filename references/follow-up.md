# Evaluate what follows development

After task work, including verification-only runs, evaluate actual project state and established goals without being asked. Rank unfinished requirements, functional gaps and adjacent improvements by user value, relevance, effort and dependencies. Prefer functional progress over housekeeping. Choose one primary action and at most two useful alternatives; never invent filler. Preserve the read-only stop boundaries of status, help and advice modes.

Label original unfinished scope REQUIRED, keep progress active and finish it when possible; use `next` if blocked. Do not recast it as a completed task's follow-up. Use RECOMMENDED for the most valuable logical improvement and OPTIONAL for nonessential enhancements. Recommendations are advisory: generating them does not authorize implementing them in this invocation.

Persist `recommendations` with `primary:{kind,action,reason}` and `alternatives:[...]`. Each action must specify the change and intended result; its reason must cite current code or an established goal. When none is supported, save `primary:null`, `alternatives:[]` and a brief `reason`. Finish each task with `state-write`, saving progress and this evaluation atomically. For revalidation without changing task progress, use `recommendations-write <current-revision>` with that JSON. The existing task `next` field remains only an unfinished task's next step. `next` must revalidate saved recommendations even when Git has not changed.

Mark complete only when done. Report actual work, verification, relevant Git and the grounded next action. End with one copyable next prompt naming the recommended action and result, or a host-appropriate NEEF command when that is the useful direction. A bare next command must not hide the actual recommendation. When blocked or pausing, give the reason in one line, keep preconditions in prose and name the input needed. When only the user can unblock, such as approving a host prompt, changing permissions or running a step themselves, name that exact step and end with a resume command whose placeholders list what NEEF needs back, for example `/neef check 1 result: <pass/fail>, <log path>`. Never suggest diagnosing or retrying a permission or policy denial; never bypass it or repeat an unchanged blocker. When goals are exhausted, say so and invite the next goal. Unfinished work reports REQUIRED scope and the host's `neef next` command. Static checks do not prove native invocation.
