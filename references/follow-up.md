# Evaluate what follows development

After task work, including verification-only runs, evaluate actual project state and established goals without being asked. Rank unfinished requirements, functional gaps and adjacent improvements by user value, relevance, effort and dependencies. Prefer functional progress over housekeeping. Sort every supported step into one of two lists. `needsYou` holds each step that cannot move without input from the user: a decision, a verdict, an approval such as a push, a credential or a manual step, including a parked idea that waits on them. `onItsOwn` holds each step NEEF can carry out once asked, with nothing further from the user. A step is never in both; when part of it can proceed, split it. Order each list by value. Start from helper `steps` and keep every saved step that still holds; drop one only when it is done or no longer supported. A finished task adds at most two new steps to the saved lists; leave further ideas out rather than queue them. A report may carry one bold idea: a more ambitious step the user may not have thought of, grounded in what the project is for. Offer it only when it is new; leave it out rather than repeat an earlier one or invent filler. All of them must cite the code or an established goal; never invent filler, and an empty list is a valid result. When the task's own follow-ups run out, look wider at the project's purpose, open gaps, the parked list and the saved bold idea. The bold idea is a suggestion only, never built unasked and never a substitute for the next step. Keep the saved one in state when nothing better comes up, without showing it again. Preserve the read-only stop boundaries of status, help and advice modes.

Label original unfinished scope REQUIRED, keep progress active and finish it when possible; use `next` if blocked. Do not recast it as a completed task's follow-up. Use RECOMMENDED for the most valuable logical improvement and OPTIONAL for nonessential enhancements. Recommendations are advisory: generating them does not authorize implementing them in this invocation.

Offer a review after risky ordinary work. When a finished task outside a plan made commits that changed code in a risk area listed in `references/importance.md` (sign-in, permissions, secrets, deleting or migrating data, a shared or public API, money, irreversible operations), or a file most of the project runs through, add one RECOMMENDED `onItsOwn` step: the host's `neef-challenge` command naming that task's first and last commit, such as `/neef-challenge the commits a1b2c3d through e4f5a6b`. A blocked report's user step and any REQUIRED step stay ahead of it. A task without commits gets no offer. Never run the review unasked; a plan keeps its own challenge.

Persist `recommendations` with `needsYou:[{kind,action,reason}]`, `onItsOwn:[...]` (up to 20 steps each) and `boldIdea:"<command> — <intended result>"`; the helper keeps the full lists beside the state, returns them as `steps` from status and next, and adds each save to the dated idea board shown in status. Each action must specify the change and intended result; a `needsYou` action names the exact answer or step needed; each reason must cite current code or an established goal. When no step is supported, save both lists empty with a brief `reason`, with a bold idea only when there is a new one. The older `primary`/`alternatives` form still saves, as `onItsOwn` with an empty `needsYou`. Finish each task with `state-write`, saving progress and this evaluation atomically. For revalidation without changing task progress, use `recommendations-write <current-revision>` with that JSON. The existing task `next` field remains only an unfinished task's next step. `next` must revalidate saved steps even when Git has not changed.

Mark complete only when done. Report actual work, verification, relevant Git, the suggestions and the backlog line. Every step is a copyable host-syntax NEEF command carrying its action, followed by its intended result; never a bare prose prompt. Mark the one step to do next as recommended; a bare next command must not hide the actual recommendation. When blocked or pausing, give the reason in one line, keep preconditions in prose and put the input needed first under Suggestions. When only the user can unblock, such as approving a host prompt, changing permissions or running a step themselves, name that exact step there with a resume command whose placeholders list what NEEF needs back, for example `/neef check 1 result: <pass/fail>, <log path>`. A check NEEF marked before showing its steps and is waiting for with helper `wait-file` is not a blocker: say that NEEF is watching, name the time limit, and give a plain resume command only as a fallback (`references/completion.md`). Once that wait times out or is stopped, it is a blocker like any other user step and gets the resume command with its placeholders. Never suggest diagnosing or retrying a permission or policy denial; never bypass it or repeat an unchanged blocker. When goals are exhausted, say so and invite the next goal under Suggestions. Unfinished work reports REQUIRED scope and the host's `neef next` command. Static checks do not prove native invocation.

## Report layout

The final reply is one self-contained summary card. The user reads only this reply, so never point back to earlier messages: restate every answer, finding, decision, user step and blocker that still matters. Keep progress updates during the turn to one line each, at milestones only.

Task and mode reports (development, plan, challenge, ask, next) use this layout, with a blank line between sections:

- `### <status emoji> <result headline>`: one line saying what happened, using ✅ done, 🟡 partly done, 🛑 blocked or ⏸️ waiting.
- **What changed:** short bullets of the practical result, then changed files as one bullet of code-formatted paths, or "No files changed".
- **Checks:** one line per check with ✅ passed, ❌ failed or ⏭️ skipped and why; REQUIRED gaps first. Add `Decided for you:` here when shaping requires it.
- **Suggestions:** the three most valuable steps across `needsYou` and `onItsOwn` as one numbered list, each `` `<command>` → <intended result> ``. End a `needsYou` step with `· needs you` and name the exact answer or action needed. Write `Nothing right now` when both lists are empty. When every remaining step is OPTIONAL, open the section with `Good place to stop.` so the user can end here. Blocked reports put the exact user step first, with its resume command. Mark exactly one step `(recommended)` and repeat its command alone in a fenced code block under the list, so the next move is one copy away.
- **Backlog:** one line counting the lists as just saved: `N tasks left, M can run without you`, where N is every `needsYou` and `onItsOwn` step and M the `onItsOwn` steps. The saved lists stay complete; only the reply is short.
- **Bold idea:** only when this report has a new one: the saved `boldIdea` as one bullet in the same form, `` `<command>` — <intended result> ``, last in the reply. Omit the section otherwise.

Size is a guideline: about five lines per section, summarizing the rest. Omit nothing required. `help`, `status` and `style` keep their own formats, and one-line answers stay short. While a plan is unfinished, the latest helper `ribbon` closes the reply verbatim in a plain code block after the card: a headline saying what is happening (🚀 working, 🛑 stuck, ⏸️ waiting, ✅ complete) over a percent bar. Explanation styles change tone, never these sections.
