# NEEF

**No-nonsense Engineering & Execution Framework**

Navigate → Execute → Evaluate → Follow-up

- **Navigate:** Understand the task, codebase, context and relevant decisions.
- **Execute:** Implement autonomously with minimal overhead.
- **Evaluate:** Verify proportionately and identify meaningful improvements.
- **Follow-up:** Recommend the next valuable action and maintain momentum.

These principles guide the existing workflow; they are not mandatory phases. The command name remains `neef`.

One explicit skill for autonomous development in Claude Code (`/neef`) and Codex (`$neef`). Modes: task, shape [--deep], plan, challenge [--deep], options, ask, setup, next, continue, status, help, doctor. Node 20+ and Git are required. No dependencies, daemon, or mandatory project setup.

Each mode also has a directly invokable subskill: `$neef-task`, `$neef-shape`, `$neef-plan`, `$neef-challenge`, `$neef-options`, `$neef-ask`, `$neef-setup`, `$neef-next`, `$neef-continue`, `$neef-status`, `$neef-help`, and `$neef-doctor`. Claude uses the matching `/neef-…` commands. Arguments and flags work as before, for example `$neef-shape --deep <idea>`. These explicit-only aliases read the same canonical Neef instructions and share its state and safety checks. Hyphenated names work on both hosts; no colon-named skill directories are required on Windows.

Maintain this source here. Run `node scripts/install.mjs` for a read-only installation plan, then `node scripts/install.mjs --apply` to synchronize the two skill copies and shared runtime. Existing managed files are hash checked and backed up before replacement; edited or unmanaged files stop installation. Unrelated agent configuration is untouched. Reinstall after source changes. Restart an agent session to refresh discovery.

The runtime lives at `~/.neef/neef.mjs`; `node <absolute-runtime-path> help` describes its commands. Shared state and Git baselines live outside projects under `~/.neef`. Every mutating helper checks that storage, including resolved directory links, stays outside the project before creating files, locks or branches. Set `NEEF_HOME` and `NEEF_USER_HOME` to isolated directories for tests. State uses canonical repository paths, SHA-256 identifiers, revision checks, exclusive locks, atomic replacement, and one recovery backup. Never remove a lock without checking its recorded owner.

`$neef setup` or `/neef setup` inspects project structure, manifests, languages, frameworks, entry points, instructions, command definitions, Git conventions and safety. The agent adds a short architecture summary from relevant source. Discovery never executes project commands or writes project-local files. Stable facts live in `context` in the existing per-project state JSON; transient task fields remain separate and unchanged. Repeating unchanged setup leaves the state byte-for-byte intact. Ordinary tasks bootstrap minimal context automatically through `begin`, without a setup requirement. Explicit setup refreshes deeper context; task writes and recovery preserve it. Bounded scans skip dependencies, build output and links; warnings identify partial discovery. Commands are discovered, not verified as runnable, and cached facts must be checked against current instructions.

After every development task, NEEF evaluates established goals and actual project state, then saves one primary recommendation and up to two useful alternatives in `recommendations` in that same state file. Actions are REQUIRED (unfinished original scope), RECOMMENDED (logical next improvement), or OPTIONAL (nonessential enhancement), each with an executable task description and grounded reason. Completed task writes require an explicit evaluation; unsupported suggestions are recorded as no useful action rather than invented. Recommendations never expand the current task automatically.

`$neef continue` / `/neef continue` resumes unfinished work. `$neef next` / `/neef next` finds and executes the highest-value supported action after completion, then saves what comes afterward. It investigates missing plans and technical dependencies, using roadmap goals (including GSD documents) as context while respecting mandatory instructions. Saved advice is revalidated; an empty list triggers discovery. Concrete blockers name the smallest required user input, and an invocation without meaningful progress never recommends invoking `next` again. See [next guidance](references/next.md). The helper stays read-only: it returns advisory candidates, current Git state and a discovery directive, never executes saved text, and exposes a previous no-action evaluation separately as `savedReason`. Active tasks block `next` and direct the user to `continue`. The transient task `next` field stays separate from recommendations. `recommendations-write <revision>` refreshes advice without replacing context or task progress.

`$neef shape <task>` / `/neef shape <task>` inspects code first, then asks only consequential unanswered questions, one at a time, with concrete choices and a recommended answer. Standard shaping stops at five questions (usually one to three); `shape --deep <task>` explores dependent design tradeoffs until meaningful uncertainty is resolved or the user stops. Ordinary tasks get at most two targeted questions and implement directly when clear. Counts and a pending question live in task `next`; agreed constraints live in `decisions`. Active same-task writes preserve both when omitted; completed/new tasks clear the pending step. After real answers, NEEF implements automatically unless discussion-only was requested, then generates next recommendations. No separate skill, interview runtime, specification documents or dependency is used; see [the integrated guidance](references/shape.md).

`$neef plan <feature>` / `/neef plan <feature>` inspects the code and automatically sizes a plan for the whole feature: one short implementation phase for bounded work, or a roadmap with dependencies and acceptance criteria for architectural changes. It saves the plan in existing external shared state and stops, leaving project files and Git unchanged. `$neef-plan <feature>` is the direct alias. Each `continue` executes at most one ready phase and stops after verification; the feature stays active until all phases are accepted. No separate planning files, dependencies or required setup are introduced. See [plan guidance](references/plan.md).

`$neef challenge <topic>` / `/neef challenge <topic>` critiques existing code or an approach using source evidence, ranks confirmed problems and potential concerns by impact, severity and effort, and recommends one improvement with up to two alternatives. `challenge --deep` examines architectural, technical and UX implications more thoroughly. It leaves project files and Git unchanged, runs no project commands, and never implements. Only concise external recommendations may be saved (even before a project has task state) for a later `next` invocation, which revalidates them. See [challenge guidance](references/challenge.md). These modes are optional; ordinary tasks still implement directly.

`$neef-options` (or `$neef options`) inspects the current project and presents 3–5 ranked actions with evidence, tradeoffs, relative effort, dependencies and exact commands. It gives fewer choices when fewer are justified. It preserves unfinished work and uses current context and saved advice without changing files, Git or external state. Reply with a number to execute that clearly selected action in this chat, or refine the choices. The advice request itself executes nothing. Unlike `next`, options lets you choose the work.

`$neef-ask <description>` (or `$neef ask <description>`) recommends the best existing workflow for a natural-language goal and provides its exact invocation, then stops. For example, `$neef-ask I want a saved plan for profile migration before implementation` recommends `$neef plan Plan profile migration before implementation`, while an unfinished matching task may call for `continue`. Missing or materially ambiguous goals get one targeted question. Advice uses the same [shared guidance](references/advisor.md) as options; there is no keyword router, dependency, new state format or automatic execution. Claude uses the corresponding `/neef-options` and `/neef-ask` forms.

Future prototype design (not implemented): use `prototype` as the canonical name and `proto` as its alias. Shape resolves what to build and, under its existing contract, implements unless explicitly discussion-only. Prototype would discover what works through a bounded working demonstration; NEEF would build and verify the approved production solution. Keep demonstrations isolated in a clearly identified scratch location, with no production imports, user-data changes or automatic promotion. Prefer interactive results when useful, but an executable algorithm comparison, API example or architecture spike may answer the question better than a UI. Explore 2–3 distinct concepts only when they test meaningful alternatives; avoid a mandatory concept count. Show how to run or inspect the demo, its limits and the decision it informs, with only checks needed to establish that demonstration. Natural follow-ups refine the same scratch artifact. Approval hands the selected concept, findings, constraints and acceptance criteria to `$neef` for a separate production task; it does not make experimental code production-ready. A future route and alias should reuse the current installer and external continuity rather than add another orchestration system. Neither prototype name is advertised as an available command today.

Git commits require a before-edit baseline and inspection of a prepared diff. Files dirty at baseline are refused. A reviewed token expires on any visible working-tree or HEAD change. Explicit selected files are committed through a private Git index while the real index is locked; unrelated edits remain outside the commit, and failed commits leave the real index intact. The helper cannot identify the author of edits made after a baseline: the calling agent must confirm ownership. Overlapping changes are preserved and left uncommitted. Hooks remain enabled and run as trusted project code. No push or merge is performed.

Run `npm run check` for focused disposable-repository tests. Installed configuration checks do not prove fresh agent discovery or native invocation; those require separate host smoke tests.

Explicit-only metadata follows [Claude Code skills](https://code.claude.com/docs/en/skills) and [OpenAI skill conventions](https://learn.chatgpt.com/docs/build-skills). The two installations share the same instructions and runtime. Native agent delegation is chosen by the agent when independent work benefits from it.
