# NEEF

**No-nonsense Engineering & Execution Framework**

Navigate → Execute → Evaluate → Follow-up

**Build as fast as you can think of it. NEEF keeps every step safe to undo.** Open an empty folder and describe what you want: `/neef build a booking page for my salon`. NEEF creates Git on `main`, picks a sensible stack without asking, builds and verifies the first working version, commits it, and hands it over running with its local URL or run command. In existing projects it moves just as fast while keeping their stack, patterns and tooling: smallest working change, focused checks, frequent safe commits and one concrete next step. No per-project setup is required. The goal NEEF is measured against is in [the vision](docs/vision.md).

## Get your first app running

You need Claude Code or Codex, Node.js 20+ and Git. Install once from a local copy of the NEEF source:

```powershell
node scripts/install.mjs
node scripts/install.mjs --apply
```

The first command previews the installation (add `--dry-run` for a readable list of `create`, `update`, `unchanged` or `remove` per path). The second installs for both hosts, backs up managed files and preserves unrelated configuration. Restart your agent session to discover NEEF. You do not need to learn the command menu or run project setup.

Open a new empty folder in your agent and describe a useful first version:

| Host | First request |
| --- | --- |
| Codex | `$neef build a local booking app for my salon. Let me add a customer booking, see the bookings, and keep them after restarting the app.` |
| Claude Code | `/neef build a local booking app for my salon. Let me add a customer booking, see the bookings, and keep them after restarting the app.` |

Expect a clear interface with that complete flow, saved local data, checks of the requested behavior, a scoped commit and a local URL or exact run command. Stack selection and project dependencies are NEEF's job. A first version uses sample data and local storage; payments, accounts and public hosting are separate requests.

Once it works, describe the next change normally, such as “let me cancel a booking.” To resume unfinished work in another session, use `$neef next` or `/neef next`. NEEF reads its saved decisions and checks them against the current project before continuing. Real build time depends on the request, model and environment; the landing-page timeline is illustrative.

## How NEEF compares

Hosted app builders such as Lovable, Bolt.new and Replit Agent also turn a prompt into an app, but your code lives on their platform. NEEF runs on your machine, in the Claude Code or Codex you already use, and also works in existing projects with their current stack. Workflow frameworks such as Spec Kit, BMAD Method and Superpowers add structure to those same agents, but most of them want a spec, a plan or role documents before any code is written. NEEF goes from a request straight to verified, committed work, and planning is optional. For details and sources, see the [comparison](docs/competitors.md).

## Explanation style

Simple is the initial default: short, everyday language with exact actions when you need to do something. Guided adds numbered steps and brief reasons. Technical explains what changed, where, why and how it was checked. Kid explains like you are 12, with everyday words and an example for each new idea.

Use `$neef style guided` in Codex or `/neef style guided` in Claude Code to save a default across all projects. Replace `guided` with `simple`, `technical` or `kid`; omit the name to see the current setting. Add `--here` (for example `/neef style kid --here`) to set a style for the current project only; `/neef style clear --here` returns it to the global default. Add "use Technical for this task" to a request for a temporary override. Styles affect explanations only, including questions and progress updates. Every style retains the instructions and evidence you need.

The preference lives in `~/.neef/preferences.json` (or `NEEF_HOME`), separate from project task state. Changing it preserves the previous file as `.bak`; reinstalling NEEF preserves the preference. Start a fresh agent session after installing updated skill instructions.

## Importance

Importance sets how much testing and independent checking a task gets, so exploring stays light and risky work gets scrutiny. `explore` writes no new tests and checks by running the thing. `normal` (the default) adds focused tests only for behavior you have settled. `important` adds tests per required outcome and has a fresh second agent re-verify them before completion. It never changes permissions or required evidence.

Set a default with `/neef importance important` (`$neef importance …` in Codex), add `--here` for this project only, or `/neef importance clear --here` to remove the override. Give one task its own level with `--importance explore`. A task's level is saved in its state, so `next` resumes at it. NEEF may suggest a higher level for risky work (auth, deletion, migrations, shared APIs) and asks first; it never lowers the level itself. See [importance](references/importance.md).

## How NEEF works

- **Navigate:** Understand the task, codebase, context and relevant decisions.
- **Execute:** Implement autonomously with minimal overhead.
- **Evaluate:** Verify proportionately and identify meaningful improvements.
- **Follow-up:** Recommend the next valuable action and maintain momentum.

The four zones form the default prompt contract. Their rules apply throughout the work; headings appear only when useful, and small tasks keep short replies. User prompts can stay in natural language. They are not mandatory phases or extra approval steps, and every mode keeps its existing write permissions and stop boundary. The command name remains `neef`.

One explicit skill for autonomous development in Claude Code (`/neef`) and Codex (`$neef`). The modes are listed below. Node 20+ and Git are required. No dependencies, daemon, or mandatory project setup.

Three commands are enough to start: `neef <what you want>` builds or changes something, `neef next` continues or does the most useful next thing, and `neef ask <goal>` writes the right command when you are not sure how to ask. Four more are there when you need them: `shape` for a rough idea, `plan` for bigger work, `prototype` to try something in a scratch folder, and `challenge` for an honest review that changes nothing, including of the last finished work or the documentation. The rest are settings and diagnostics.

Invoke a mode as `/neef <mode>` in Claude Code or `$neef <mode>` in Codex. `help` shows the three starting commands first, then the same list grouped by intent. Each guide holds the full rules for its mode.

Each main mode also has a directly invokable subskill with its description shown in the skill picker: `$neef-task`, `$neef-shape`, `$neef-plan`, `$neef-challenge`, `$neef-prototype`, `$neef-ask`, `$neef-setup`, `$neef-next`, `$neef-status` and `$neef-help`. Claude uses the matching `/neef-…` commands. The rare `style`, `importance` and `doctor` work only through `$neef`/`/neef`. Former commands and aliases (`review`, `docs`, `merge`, `options`, `auto`, `proto`, `prompt`, `continue`) are gone; reinstalling retires their old subskill folders when unedited. Arguments and flags work as before, for example `$neef-shape --deep <idea>`. These explicit-only aliases read the same canonical Neef instructions and share its state and safety checks. Hyphenated names work on both hosts; no colon-named skill directories are required on Windows.

Maintain this source here and rerun the quick-start installer after source changes. Existing managed files are hash checked and backed up before replacement; edited or unmanaged files stop installation. Unrelated agent configuration is untouched. Restart an agent session to refresh discovery.

The runtime lives at `~/.neef/neef.mjs`; `node <absolute-runtime-path> help` describes its commands. Shared state and Git baselines live outside projects under `~/.neef`. Every mutating helper checks that storage, including resolved directory links, stays outside the project before creating files, locks or branches. Set `NEEF_HOME` and `NEEF_USER_HOME` to isolated directories for tests. State uses canonical repository paths, SHA-256 identifiers, revision checks, exclusive locks, atomic replacement, and one recovery backup per file. A project's state is `state/<id>.json`; a saved plan lives beside it in `state/<id>.plan.json`, and each file keeps one `.bak`. The state stays under 8 KiB and 40 lines and records the plan's hash, so one lock and revision cover both; the plan may reach 32 KiB. Never remove a lock without checking its recorded owner.

`$neef setup` or `/neef setup` inspects project structure, manifests, languages, frameworks, entry points, instructions, command definitions, Git conventions and safety. The agent adds a short architecture summary from relevant source. Discovery never executes project commands. Explicit setup adds a managed next-prompt rule to root AGENTS.md and CLAUDE.md, creating missing files and preserving existing content. Original files are backed up under ~/.neef/backups with restore metadata; copied bytes are verified. Linked files and edited or malformed managed blocks are refused. Repeating setup leaves matching blocks untouched. Ordinary project replies then end with one host-syntax NEEF command carrying the concrete request, never a bare prose prompt: modes use their hyphenated skill (`/neef-next ...` in Claude Code, `$neef-next ...` in Codex), and plain tasks use `/neef ...` or `$neef ...`. Waiting replies put the needed answer in the command, and exhausted goals suggest `/neef-shape <next goal>` without inventing work. Rerunning setup upgrades an unedited earlier block in place. Suggestions never execute automatically; NEEF remains explicit-only. Rerun setup in previously configured projects to add the rule. Stable facts live in `context` in the existing per-project state JSON; transient task fields remain separate and unchanged. Repeating unchanged setup leaves the state byte-for-byte intact. Ordinary tasks bootstrap minimal context automatically through `begin`, without a setup requirement. Explicit setup refreshes deeper context; task writes and recovery preserve it. Bounded scans skip dependencies, build output and links; warnings identify partial discovery. Commands are discovered, not verified as runnable, and cached facts must be checked against current instructions.

After every development task, NEEF evaluates established goals and actual project state, then saves one primary recommendation and up to two useful alternatives in `recommendations` in that same state file. Actions are REQUIRED (unfinished original scope), RECOMMENDED (logical next improvement), or OPTIONAL (nonessential enhancement), each with an executable task description and grounded reason. Completed task writes require an explicit evaluation; unsupported suggestions are recorded as no useful action rather than invented. Recommendations never expand the current task automatically. The `next` helper is read-only: it returns either a `resume` signal for an unfinished task or the saved advisory candidates for the agent to revalidate, and `recommendations-write` refreshes that advice when no task work occurred; see [next guidance](references/next.md).

The internal `prototype-workspace [slug]` helper lists recent per-project demos when no slug is supplied, or allocates a unique external directory under `~/.neef/prototypes/<project-id>/` (respecting NEEF_HOME). It never changes production files, Git or task state; linked or project-local storage is refused. The demo README records the question, concepts, exact run command, findings, refinements, shortcuts and production acceptance criteria. Fresh prototype sessions use that record; `next` retains its existing production-task behavior. Keep dependencies, build output and synthetic data in scratch, without production runtime imports or live-system connections. Run only checks needed for the demonstration. Approval records the chosen design and produces a concrete NEEF implementation command; it does not automatically promote code. An explicit production implementation request uses the normal NEEF safeguards. Both hosts install the same [prototype guidance](references/prototype.md); Claude uses `/neef-prototype`.

Development prioritizes fast, scoped changes and focused checks on main, with frequent commits of completed increments. NEEF creates no branches or worktrees; `begin` preserves the current branch. In a linked Git worktree NEEF works and commits on that worktree's checked-out branch, with its own task state; once the task is saved complete after its last commit, the `merge` helper brings the branch into main in the main folder (fast-forward when possible, otherwise one merge commit). It refuses conflicts, a main folder off main or with staged or in-progress work, and Git's own refusal protects local edits there; a failed merge leaves both sides as they were, and nothing is pushed or deleted. After a merge commit the agent reruns focused checks in the main folder. In a completely empty folder without Git, `begin` initializes Git on `main` and reports `gitInitialized`; an empty repository reports `greenfield`, which loads the [start guidance](references/start.md): decide the stack, commit the first working version, hand it over running. Non-empty folders without Git are never initialized automatically; the agent asks first. Runnable work in any project ends verified to start, with its run command or local URL. In the main folder on another branch, project edits and commits pause until main is selected; existing work is preserved. Git commits require a before-edit baseline and inspection of a prepared diff. Files dirty at baseline are refused. A reviewed token records only hashes of the reviewed diff and working tree, never the diff itself, and expires on any visible working-tree or HEAD change. Explicit selected files are committed through a private Git index while the real index is locked; unrelated edits remain outside the commit, and failed commits leave the real index intact. The helper cannot identify the author of edits made after a baseline: the calling agent must confirm ownership. Overlapping changes are preserved and left uncommitted. Hooks remain enabled and run as trusted project code. No push is performed, and nothing merges except as above or through `merge`.

Records stay light: an ordinary task completes on a short verification note saying what was done and checked. Work with a saved plan, or marked `important`, also records requested outcomes in a compact `outcomes` array, each with an id, description, required flag, status and evidence; there the helper rejects completion without passing results and evidence for every required outcome. Cleared blockers and finished plan phases are always required. A new project starts at `explore`: NEEF runs it and tries the main flow, and writes no test files until a first working version exists. Optional checks add no gate. The helper checks record consistency, not whether reported behavior really works. Legacy state remains readable; the stronger checks apply when completing a task. This uses the same commands and normal state saves, without extra plans or approval steps. See [completion guidance](references/completion.md).

Longer work uses those same notes: same-task saves retain omitted decisions, evidence and blockers, and active same-task saves also retain omitted next steps; completing a task requires explicitly clearing saved blockers. Explicit empty strings clear resolved or obsolete notes; omitted notes start empty for a different task. On resumption, reconcile saved progress with current files and Git, retain settled decisions, and rerun only checks whose evidence is affected by changes. No extra command, history store or checkpoint step is needed.

Run `npm run check` for focused disposable-repository tests. Installed configuration checks do not prove fresh agent discovery or native invocation; those require separate host smoke tests.

Maintainers can preview the matching empty-folder booking-app regression with `node scripts/greenfield-smoke.mjs --plan` (read-only). The opt-in `--run` uses fresh installed hosts and disposable projects, checks creation/listing and persistence after a server restart, and records actual elapsed time without a speed threshold. Its own server checks allow six seconds for readiness, two seconds per request and two seconds for shutdown; repeated cleanup shares the original result and targets only the retained child handle. A shutdown timeout reports unconfirmed cleanup and releases checker references without another kill attempt. `--claude-only` or `--codex-only` selects one host. Codex keeps its workspace sandbox and approval review enabled; the scenario requests scoped approval for exact Git-writing helper operations before touching protected metadata. The empty-folder flag only permits starting outside a Git repository, and Git discovery is confined to the disposable artifact directory. No global permission settings are changed. It stops at the first failure; inspect the recorded result and respect any host denial before considering another run. The checker verifies HTTP behavior and interface source, not browser interaction or visual quality. This is maintenance tooling, never an extra step for ordinary NEEF tasks.

All six installed-host smoke runners share `scripts/host-smoke.mjs`: Codex retains its workspace sandbox and approval review, fixtures use main, and resumed sessions retain the same safety settings. Each host turn has a ten-minute deadline (`NEEF_SMOKE_TIMEOUT_MS` overrides it); local helper/test subprocesses have a thirty-second deadline. Timeout logs are preserved and only the retained host is stopped, with two seconds to confirm exit. Tools it started may need inspection before another run. On Windows the runner starts the native host executable directly, avoiding shell quoting and orphaned npm shims. These scripts run from this checkout and require no skill reinstall. Deterministic launcher checks run with `node --test tests/host-smoke.test.mjs`; actual model sessions remain opt-in.
