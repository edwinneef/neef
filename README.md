# NEEF

**No-nonsense Engineering & Execution Framework**

Navigate → Execute → Evaluate → Follow-up

**From idea to a running project, fast.** Open an empty folder and describe what you want: `/neef build a booking page for my salon`. NEEF creates Git on `main`, picks a sensible stack without asking, builds and verifies the first working version, commits it, and hands it over running with its local URL or run command. In existing projects it moves just as fast while keeping their stack, patterns and tooling: smallest working change, focused checks, frequent safe commits and one concrete next step. No per-project setup is required.

## Get your first app running

You need Claude Code or Codex, Node.js 20+ and Git. Install once from a local copy of the NEEF source:

```powershell
node scripts/install.mjs
node scripts/install.mjs --apply
```

The first command previews the installation. The second installs for both hosts, backs up managed files and preserves unrelated configuration. Restart your agent session to discover NEEF. You do not need to learn the command menu or run project setup.

Open a new empty folder in your agent and describe a useful first version:

| Host | First request |
| --- | --- |
| Codex | `$neef build a local booking app for my salon. Let me add a customer booking, see the bookings, and keep them after restarting the app.` |
| Claude Code | `/neef build a local booking app for my salon. Let me add a customer booking, see the bookings, and keep them after restarting the app.` |

Expect a clear interface with that complete flow, saved local data, checks of the requested behavior, a scoped commit and a local URL or exact run command. Stack selection and project dependencies are NEEF's job. A first version uses sample data and local storage; payments, accounts and public hosting are separate requests.

Once it works, describe the next change normally, such as “let me cancel a booking.” To resume unfinished work in another session, use `$neef next` or `/neef next`. NEEF reads its saved decisions and checks them against the current project before continuing. Real build time depends on the request, model and environment; the landing-page timeline is illustrative.

## Explanation style

Simple is the initial default: short, everyday language with exact actions when you need to do something. Guided adds numbered steps and brief reasons. Technical explains what changed, where, why and how it was checked.

Use `$neef style guided` in Codex or `/neef style guided` in Claude Code to save a default across all projects. Replace `guided` with `simple` or `technical`; omit the name to see the current setting. Add "use Technical for this task" to a request for a temporary override. Styles affect explanations only, including questions and progress updates. Every style retains the instructions and evidence you need.

The preference lives in `~/.neef/preferences.json` (or `NEEF_HOME`), separate from project task state. Changing it preserves the previous file as `.bak`; reinstalling NEEF preserves the preference. Start a fresh agent session after installing updated skill instructions.

## How NEEF works

- **Navigate:** Understand the task, codebase, context and relevant decisions.
- **Execute:** Implement autonomously with minimal overhead.
- **Evaluate:** Verify proportionately and identify meaningful improvements.
- **Follow-up:** Recommend the next valuable action and maintain momentum.

The four zones form the default prompt contract. Their rules apply throughout the work; headings appear only when useful, and small tasks keep short replies. User prompts can stay in natural language. They are not mandatory phases or extra approval steps, and every mode keeps its existing write permissions and stop boundary. The command name remains `neef`.

One explicit skill for autonomous development in Claude Code (`/neef`) and Codex (`$neef`). Modes: task, shape [--deep] [--discuss] [idea], plan, challenge [--deep], prototype (proto), options [goal] (ask), setup, next (continue), status, help, style [simple|guided|technical], doctor. Node 20+ and Git are required. No dependencies, daemon, or mandatory project setup.

Each main mode also has a directly invokable subskill with its description shown in the skill picker: `$neef-task`, `$neef-shape`, `$neef-plan`, `$neef-challenge`, `$neef-prototype`, `$neef-options`, `$neef-setup`, `$neef-next`, `$neef-status` and `$neef-help`. Claude uses the matching `/neef-…` commands. Aliases (`proto`, `ask`, `continue`) and the rare `doctor` work only through `$neef`/`/neef`; reinstalling retires their old subskill folders when unedited. Arguments and flags work as before, for example `$neef-shape --deep <idea>`. These explicit-only aliases read the same canonical Neef instructions and share its state and safety checks. Hyphenated names work on both hosts; no colon-named skill directories are required on Windows.

Maintain this source here and rerun the quick-start installer after source changes. Existing managed files are hash checked and backed up before replacement; edited or unmanaged files stop installation. Unrelated agent configuration is untouched. Restart an agent session to refresh discovery.

The runtime lives at `~/.neef/neef.mjs`; `node <absolute-runtime-path> help` describes its commands. Shared state and Git baselines live outside projects under `~/.neef`. Every mutating helper checks that storage, including resolved directory links, stays outside the project before creating files, locks or branches. Set `NEEF_HOME` and `NEEF_USER_HOME` to isolated directories for tests. State uses canonical repository paths, SHA-256 identifiers, revision checks, exclusive locks, atomic replacement, and one recovery backup. Never remove a lock without checking its recorded owner.

`$neef-help` (or `$neef help`; `/neef-help` in Claude) groups commands by intent: choose what to do, explore before building, build or keep moving, and understand the project and installation. Each command shows what it changes and where it stops, including Shape's implementation default, Plan's save-and-stop boundary, Prototype's scratch isolation, and Options versus Next. Host syntax, flags and direct aliases remain visible. One built-in command catalog supplies both discovery and help metadata; help remains read-only and adds no separate UI.

`$neef setup` or `/neef setup` inspects project structure, manifests, languages, frameworks, entry points, instructions, command definitions, Git conventions and safety. The agent adds a short architecture summary from relevant source. Discovery never executes project commands. Explicit setup adds a managed next-prompt rule to root AGENTS.md and CLAUDE.md, creating missing files and preserving existing content. Original files are backed up under ~/.neef/backups with restore metadata; copied bytes are verified. Linked files and edited or malformed managed blocks are refused. Repeating setup leaves matching blocks untouched. Ordinary project replies then end with one host-syntax NEEF command (`/neef ...` or `$neef ...`) carrying the concrete request, never a bare prose prompt; waiting replies put the needed answer in the command, and exhausted goals suggest `neef shape <next goal>` without inventing work. Rerunning setup upgrades an unedited earlier block in place. Suggestions never execute automatically; NEEF remains explicit-only. Rerun setup in previously configured projects to add the rule. Stable facts live in `context` in the existing per-project state JSON; transient task fields remain separate and unchanged. Repeating unchanged setup leaves the state byte-for-byte intact. Ordinary tasks bootstrap minimal context automatically through `begin`, without a setup requirement. Explicit setup refreshes deeper context; task writes and recovery preserve it. Bounded scans skip dependencies, build output and links; warnings identify partial discovery. Commands are discovered, not verified as runnable, and cached facts must be checked against current instructions.

After every development task, NEEF evaluates established goals and actual project state, then saves one primary recommendation and up to two useful alternatives in `recommendations` in that same state file. Actions are REQUIRED (unfinished original scope), RECOMMENDED (logical next improvement), or OPTIONAL (nonessential enhancement), each with an executable task description and grounded reason. Completed task writes require an explicit evaluation; unsupported suggestions are recorded as no useful action rather than invented. Recommendations never expand the current task automatically.

`$neef next` / `/neef next` resumes unfinished work first (`continue` is an alias); otherwise it finds and executes the highest-value supported action, then saves what comes afterward. It investigates missing plans and technical dependencies, using roadmap goals (including GSD documents) as context while respecting mandatory instructions. Saved advice is revalidated; an empty list triggers discovery. Concrete blockers name the smallest required user input, and an invocation without meaningful progress never recommends invoking `next` again. See [next guidance](references/next.md). The helper stays read-only: it returns advisory candidates, current Git state and a discovery directive, never executes saved text, and exposes a previous no-action evaluation separately as `savedReason`. With an active task the helper returns `resume` and no candidates, so the agent finishes that task before choosing new work. The transient task `next` field stays separate from recommendations. `recommendations-write <revision>` refreshes advice without replacing context or task progress.

`$neef shape <task>` / `/neef shape <task>` inspects code first, then asks only consequential unanswered questions, one at a time, with concrete choices and a recommended answer. Bare `$neef shape` offers three small project-specific starter ideas and waits for a numbered choice or your own idea, without changing files, Git or saved task state. Standard shaping stops at five questions (usually one to three); `shape --deep <task>` explores dependent design tradeoffs until meaningful uncertainty is resolved or the user stops. Ordinary tasks get at most two targeted questions and implement directly when clear. Counts and a pending question live in task `next`; agreed constraints live in `decisions`. Active same-task writes preserve both when omitted; completed/new tasks clear the pending step. After real answers, NEEF implements automatically unless discussion-only was requested, then generates next recommendations. No separate skill, interview runtime, specification documents or dependency is used; see [the integrated guidance](references/shape.md).

Use `$neef shape --discuss <idea>` (Claude: `/neef shape --discuss <idea>`) to explore and save decisions without building. Project files and Git stay unchanged; discussion-only remains in effect on `next` or `continue` until you explicitly request implementation. Combine it with `--deep` in either order, or omit the idea to start with suggestions. The direct `$neef-shape` / `/neef-shape` aliases support the same flags.

`$neef plan <feature>` / `/neef plan <feature>` inspects the code and automatically sizes a plan for the whole feature: one short implementation phase for bounded work, or a roadmap with dependencies and acceptance criteria for architectural changes. It saves the plan in existing external shared state and stops, leaving project files and Git unchanged. `$neef-plan <feature>` is the direct alias. One `next` runs all ready phases until complete or blocked by essential user input or authority, including independent phases when another is blocked. It saves evidence and commits completed increments along the way. No separate planning files, dependencies or required setup are introduced. See [plan guidance](references/plan.md).

`$neef challenge <topic>` / `/neef challenge <topic>` critiques existing code or an approach using source evidence, ranks confirmed problems and potential concerns by impact, severity and effort, and recommends one improvement with up to two alternatives. `challenge --deep` examines architectural, technical and UX implications more thoroughly. It leaves project files and Git unchanged, runs no project commands, and never implements. Only concise external recommendations may be saved (even before a project has task state) for a later `next` invocation, which revalidates them. See [challenge guidance](references/challenge.md). These modes are optional; ordinary tasks still implement directly.

`$neef-options` (or `$neef options`) inspects the current project and presents 3–5 ranked actions with evidence, tradeoffs, relative effort, dependencies and exact commands. It gives fewer choices when fewer are justified. It preserves unfinished work and uses current context and saved advice without changing files, Git or external state. Reply with a number to execute that clearly selected action in this chat, or refine the choices. The advice request itself executes nothing. Unlike `next`, options lets you choose the work.

`$neef-options <goal>` (or `$neef ask <goal>`) recommends the best existing workflow for a natural-language goal and provides its exact invocation, then stops. For example, `$neef-options I want a saved plan for profile migration before implementation` recommends `$neef plan Plan profile migration before implementation`, while an unfinished matching task may call for `next`. Missing or materially ambiguous goals get one targeted question. Advice uses the same [shared guidance](references/advisor.md) as options; there is no keyword router, dependency, new state format or automatic execution. Claude uses `/neef-options`.

`$neef-prototype <description>` (or `$neef prototype` / `$neef proto`) build rapid isolated demonstrations to discover what works. Shape resolves what to build and implements unless discussion-only; prototype tests a bounded uncertainty through a working demo; NEEF builds the approved production solution. Visual or interaction questions favor interactive previews. Algorithms, APIs and architecture can use executable comparisons without a UI. Explore 2–3 concepts only when useful, then refine the same demo through natural follow-ups such as “make it more compact” or “combine concepts 1 and 3.”

The internal `prototype-workspace [slug]` helper lists recent per-project demos when no slug is supplied, or allocates a unique external directory under `~/.neef/prototypes/<project-id>/` (respecting NEEF_HOME). It never changes production files, Git or task state; linked or project-local storage is refused. The demo README records the question, concepts, exact run command, findings, refinements, shortcuts and production acceptance criteria. Fresh prototype sessions use that record; `next` retains its existing production-task behavior. Keep dependencies, build output and synthetic data in scratch, without production runtime imports or live-system connections. Run only checks needed for the demonstration. Approval records the chosen design and produces a concrete NEEF implementation command; it does not automatically promote code. An explicit production implementation request uses the normal NEEF safeguards. Both hosts install the same [prototype guidance](references/prototype.md); Claude uses `/neef-prototype`.

Development prioritizes fast, scoped changes and focused checks on main, with frequent commits of completed increments. NEEF creates no branches or worktrees; `begin` preserves the current branch. In a completely empty folder without Git, `begin` initializes Git on `main` and reports `gitInitialized`; an empty repository reports `greenfield`, which loads the [start guidance](references/start.md): decide the stack, commit the first working version, hand it over running. Non-empty folders without Git are never initialized automatically; the agent asks first. Runnable work in any project ends verified to start, with its run command or local URL. On another branch, project edits and commits pause until main is selected; existing work is preserved. Git commits require a before-edit baseline and inspection of a prepared diff. Files dirty at baseline are refused. A reviewed token expires on any visible working-tree or HEAD change. Explicit selected files are committed through a private Git index while the real index is locked; unrelated edits remain outside the commit, and failed commits leave the real index intact. The helper cannot identify the author of edits made after a baseline: the calling agent must confirm ownership. Overlapping changes are preserved and left uncommitted. Hooks remain enabled and run as trusted project code. No push or merge is performed.

Development records requested outcomes in a compact `outcomes` array alongside the existing decisions and verification notes. Each outcome has an id, description, required flag, status and evidence. The helper rejects completion without valid outcome records, passing results and evidence for every required outcome, cleared blockers and finished plan phases. Optional checks add no gate. The helper checks record consistency, not whether reported behavior really works. Legacy state remains readable; the stronger checks apply when completing a task. This uses the same commands and normal state saves, without extra plans or approval steps. See [completion guidance](references/completion.md).

Longer work uses those same notes: same-task saves retain omitted decisions and evidence, and active same-task saves retain omitted next steps and blockers. Explicit empty strings clear resolved or obsolete notes; omitted notes start empty for a different task. On resumption, reconcile saved progress with current files and Git, retain settled decisions, and rerun only checks whose evidence is affected by changes. No extra command, history store or checkpoint step is needed.

Run `npm run check` for focused disposable-repository tests. Installed configuration checks do not prove fresh agent discovery or native invocation; those require separate host smoke tests.

Maintainers can preview the matching empty-folder booking-app regression with `node scripts/greenfield-smoke.mjs --plan` (read-only). The opt-in `--run` uses fresh installed hosts and disposable projects, checks creation/listing and persistence after a server restart, and records actual elapsed time without a speed threshold. Its own server checks allow six seconds for readiness, two seconds per request and two seconds for shutdown; repeated cleanup shares the original result and targets only the retained child handle. A shutdown timeout reports unconfirmed cleanup and releases checker references without another kill attempt. `--claude-only` or `--codex-only` selects one host. Codex keeps its workspace sandbox and approval review enabled; the scenario requests scoped approval for exact Git-writing helper operations before touching protected metadata. The empty-folder flag only permits starting outside a Git repository, and Git discovery is confined to the disposable artifact directory. No global permission settings are changed. It stops at the first failure; inspect the recorded result and respect any host denial before considering another run. The checker verifies HTTP behavior and interface source, not browser interaction or visual quality. This is maintenance tooling, never an extra step for ordinary NEEF tasks.

All six installed-host smoke runners share `scripts/host-smoke.mjs`: Codex retains its workspace sandbox and approval review, fixtures use main, and resumed sessions retain the same safety settings. Each host turn has a ten-minute deadline (`NEEF_SMOKE_TIMEOUT_MS` overrides it); local helper/test subprocesses have a thirty-second deadline. Timeout logs are preserved and only the retained host is stopped, with two seconds to confirm exit. Tools it started may need inspection before another run. On Windows the runner starts the native host executable directly, avoiding shell quoting and orphaned npm shims. These scripts run from this checkout and require no skill reinstall. Deterministic launcher checks run with `node --test tests/host-smoke.test.mjs`; actual model sessions remain opt-in.
