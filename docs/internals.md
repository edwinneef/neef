# NEEF internals

How NEEF is built and maintained. The [README](../README.md) covers using it.

Maintain this source here and rerun the quick-start installer after source changes. Existing managed files are hash checked and backed up before replacement; edited or unmanaged files stop installation. Unrelated agent configuration is untouched, except that the prompt gate adds one marked `UserPromptSubmit` entry to `~/.claude/settings.json` and the Codex `hooks.json`; that merge never moves existing hooks, is backed up with the install and is undone by `--gate off`. Restart an agent session to refresh discovery.

The runtime lives at `~/.neef/neef.mjs`; `node <absolute-runtime-path> help` describes its commands. Shared state and Git baselines live outside projects under `~/.neef`. Every mutating helper checks that storage, including resolved directory links, stays outside the project before creating files, locks or branches. Set `NEEF_HOME` and `NEEF_USER_HOME` to isolated directories for tests. State uses canonical repository paths, SHA-256 identifiers, revision checks, exclusive locks, atomic replacement, and one recovery backup per file. A project's state is `state/<id>.json`; a saved plan lives beside it in `state/<id>.plan.json`, and each file keeps one `.bak`. The task notes stay under 8 KiB and 40 lines and record the plan's hash, so one lock and revision cover both; the plan may reach 32 KiB, and outcome evidence has its own 32 KiB. Never remove a lock without checking its recorded owner.

`$neef setup` or `/neef setup` inspects project structure, manifests, languages, frameworks, entry points, instructions, command definitions, Git conventions and safety. The agent adds a short architecture summary from relevant source. Discovery never executes project commands. Explicit setup adds a managed next-prompt rule to root AGENTS.md and CLAUDE.md, creating missing files and preserving existing content. Original files are backed up under ~/.neef/backups with restore metadata; copied bytes are verified. Linked files and edited or malformed managed blocks are refused. Repeating setup leaves matching blocks untouched. Ordinary project replies then end with one host-syntax NEEF command carrying the concrete request, never a bare prose prompt: modes use their hyphenated skill (`/neef-next ...` in Claude Code, `$neef-next ...` in Codex), and plain tasks use `/neef ...` or `$neef ...`. Waiting replies put the needed answer in the command, and exhausted goals suggest `/neef-shape <next goal>` without inventing work. Rerunning setup upgrades an unedited earlier block in place. Suggestions never execute automatically; NEEF remains explicit-only. Rerun setup in previously configured projects to add the rule. Stable facts live in `context` in the existing per-project state JSON; transient task fields remain separate and unchanged. Repeating unchanged setup leaves the state byte-for-byte intact. Ordinary tasks bootstrap minimal context automatically through `begin`, without a setup requirement. Explicit setup refreshes deeper context; task writes and recovery preserve it. Bounded scans skip dependencies, build output and links; warnings identify partial discovery. Commands are discovered, not verified as runnable, and cached facts must be checked against current instructions.

After every development task, NEEF evaluates established goals and actual project state, then saves two lists of next steps, up to 20 each: `needsYou`, which cannot move without your input, and `onItsOwn`, which NEEF can do once asked. Every final reply ends with the top three across both, a line counting how many steps are left and how many can run without you, and a bold idea only when there is a new one; when every remaining step is optional the reply says `Good place to stop`; `status` shows the top five of each. The full lists live beside the state file, which keeps the top three in `recommendations`. Actions are REQUIRED (unfinished original scope), RECOMMENDED (logical next improvement), or OPTIONAL (nonessential enhancement), each with an executable task description and grounded reason. Completed task writes require an explicit evaluation; unsupported suggestions are recorded as no useful action rather than invented. Recommendations never expand the current task automatically. The `next` helper is read-only: it returns either a `resume` signal for an unfinished task or the saved advisory candidates for the agent to revalidate, and `recommendations-write` refreshes that advice when no task work occurred; see [next guidance](../references/next.md).

The internal `prototype-workspace [slug]` helper lists recent per-project demos when no slug is supplied, or allocates a unique external directory under `~/.neef/prototypes/<project-id>/` (respecting NEEF_HOME). Both forms return the `taste` path, `~/.neef/taste.md`, which option-card runs share across projects. It never changes production files, Git or task state; linked or project-local storage is refused. The demo README records the question, concepts, exact run command, findings, refinements, shortcuts and production acceptance criteria. Fresh prototype sessions use that record; `next` retains its existing production-task behavior. Keep dependencies, build output and synthetic data in scratch, without production runtime imports or live-system connections. Run only checks needed for the demonstration. Approval records the chosen design and produces a concrete NEEF implementation command; it does not automatically promote code. An explicit production implementation request uses the normal NEEF safeguards. Both hosts install the same [prototype guidance](../references/prototype.md); Claude uses `/neef-prototype`.

Development prioritizes fast, scoped changes and focused checks on the branch you are on, with frequent commits of completed increments. NEEF creates no branches or worktrees and never switches branches; `begin` works on the current branch and the report names it when it is not main. In a linked Git worktree NEEF works and commits on that worktree's checked-out branch, with its own task state; once the task is saved complete after its last commit, the `merge` helper brings the branch into main in the main folder (fast-forward when possible, otherwise one merge commit). It refuses conflicts, a main folder off main or with staged or in-progress work, and Git's own refusal protects local edits there; a failed merge leaves both sides as they were, and nothing is pushed or deleted. After a merge commit the agent reruns focused checks in the main folder. In a completely empty folder without Git, `begin` initializes Git on `main` and reports `gitInitialized`; an empty repository reports `greenfield`, which loads the [start guidance](../references/start.md): decide the stack, commit the first working version, hand it over running. Non-empty folders without Git are never initialized automatically; the agent asks first. Runnable work in any project ends verified to start, with its run command or local URL. A detached HEAD is refused until a branch is selected; existing work is preserved. Git commits require a before-edit baseline and inspection of a prepared diff. Files dirty at baseline are refused, except files the previous baseline with the same slug, on this branch and at an ancestor HEAD, did not hold as pre-existing: `begin` lists them as `inherited`, so committing one increment never orphans another increment's uncommitted edits. A reviewed token records only hashes of the reviewed diff and working tree, never the diff itself, and expires on any visible working-tree or HEAD change. Explicit selected files are committed through a private Git index while the real index is locked; unrelated edits remain outside the commit, and failed commits leave the real index intact. The helper cannot identify the author of edits made after a baseline: the calling agent must confirm ownership. Overlapping changes are preserved and left uncommitted. Hooks remain enabled and run as trusted project code. No push is performed, and nothing merges except as above or through `merge`.

Records stay light: an ordinary task completes on a short verification note saying what was done and checked. Work with a saved plan, or marked `important`, also records requested outcomes in a compact `outcomes` array, each with an id, description, required flag, status and evidence; there the helper rejects completion without passing results and evidence for every required outcome. Cleared blockers and finished plan phases are always required. A new project starts at `explore`: NEEF runs it and tries the main flow, and writes no test files until a first working version exists. Optional checks add no gate. The helper checks record consistency, not whether reported behavior really works. Legacy state remains readable; the stronger checks apply when completing a task. This uses the same commands and normal state saves, without extra plans or approval steps. See [completion guidance](../references/completion.md).

Longer work uses those same notes: same-task saves retain omitted decisions, evidence and blockers, and active same-task saves also retain omitted next steps; completing a task requires explicitly clearing saved blockers. Explicit empty strings clear resolved or obsolete notes; omitted notes start empty for a different task. On resumption, reconcile saved progress with current files and Git, retain settled decisions, and rerun only checks whose evidence is affected by changes. No extra command, history store or checkpoint step is needed.

Run `npm run check` for focused disposable-repository tests. Installed configuration checks do not prove fresh agent discovery or native invocation; those require separate host smoke tests.

Maintainers can preview the matching empty-folder booking-app regression with `node scripts/greenfield-smoke.mjs --plan` (read-only). The opt-in `--run` uses fresh installed hosts and disposable projects, checks creation/listing and persistence after a server restart, and records actual elapsed time without a speed threshold. Its own server checks allow six seconds for readiness, two seconds per request and two seconds for shutdown; repeated cleanup shares the original result and targets only the retained child handle. A shutdown timeout reports unconfirmed cleanup and releases checker references without another kill attempt. `--claude-only` or `--codex-only` selects one host. Codex keeps its workspace sandbox and approval review enabled; the scenario requests scoped approval for exact Git-writing helper operations before touching protected metadata. The empty-folder flag only permits starting outside a Git repository, and Git discovery is confined to the disposable artifact directory. No global permission settings are changed. It stops at the first failure; inspect the recorded result and respect any host denial before considering another run. The checker verifies HTTP behavior and interface source, not browser interaction or visual quality. This is maintenance tooling, never an extra step for ordinary NEEF tasks.

All six installed-host smoke runners share `scripts/host-smoke.mjs`: Codex retains its workspace sandbox and approval review, fixtures use main, and resumed sessions retain the same safety settings. Each host turn has a ten-minute deadline (`NEEF_SMOKE_TIMEOUT_MS` overrides it); local helper/test subprocesses have a thirty-second deadline. Timeout logs are preserved and only the retained host is stopped, with two seconds to confirm exit. Tools it started may need inspection before another run. On Windows the runner starts the native host executable directly, avoiding shell quoting and orphaned npm shims. These scripts run from this checkout and require no skill reinstall. Deterministic launcher checks run with `node --test tests/host-smoke.test.mjs`; actual model sessions remain opt-in.

The [landing page](../site/README.md) uses the approved Tobacco light/dark design with reduced-motion support. Run `npm --prefix site ci`, then `npm run site:dev` to open it locally at http://127.0.0.1:4378. `npm run site:build` creates the static site in `site/dist/`.

The two installations share the same instructions and runtime. Native agent delegation is chosen by the agent when independent work benefits from it.
